# Fork notes: Jira integration

## Purpose

This fork of the Focus Board bb plugin adds an optional Jira integration: threads link to Jira tickets, a built-in sync (`lib/jira-sync-core.ts`, run every minute while the `jiraSync` setting is on) keeps a ticket/PR snapshot and drains an op queue through `acli` and `gh`, the Attention view gets a Jira column, cards get ticket chips and reason lines, Done becomes a checked request whose Jira writes wait for the operator's closeout approval, and quiet-thread reminders replace the long-idle sweep. It is off by default (`jiraEnabled=false`); with it off the board behaves like upstream.

- Design: `docs/superpowers/specs/2026-10-29-jira-integration-design.md`
- Plan: `docs/superpowers/plans/2026-10-29-jira-integration.md`
- Upstream base: `c41190c` (`git diff c41190c..HEAD --stat` lists everything this fork touches).

New files are all `lib/jira-*.ts`, `components/jira-*.tsx`, `tests/jira-*` and `tests/helpers/no-real-tools.ts`. They do not conflict with upstream. The table below lists every edit to an upstream file.

## Load-bearing contracts

- `lib/jira-schema.ts` (zod; the store parses with it): `JiraSnapshot` (version 1; `tickets`, `prs`, `mentions` shape), `GhPr`, `QueueOp` (discriminated on `op`), `OpResult`. Changing any of them means changing `lib/jira-sync-core.ts` and its test (`tests/jira-sync-core.test.ts` parses the pass's output with the real schema).
- `ThreadJiraRecord` is stored under plugin metadata key `"jira"` (`THREAD_JIRA_KEY`). It must be complete: a partial record parses as empty (`lib/jira-store.ts`). `jiraStartThreadSeed` writes a complete one.
- KV keys: `jira:snapshot`, `jira:snapshot-failure`, `jira:queue`, `jira:results`, `jira:reconcile-plan`, `jira:dismissed-suggestions`, `jira:enabled-seen`, `jira:snooze-seen`, `jira:idle-jobs`, `jira:next-steps`, `jira:refresh-requested-at`, `jira:script-seen-at` (when a sync pass last started; the name predates the built-in sync), `jira:nudge-turns`, `jira:verify-sent`, `jira:migrated-pr-unavailable` (set once the one-time startup migration cleared the old failed checks whose only reason was "PR status unavailable"), `jira:no-nudge` (threadId → true: the operator's Don't nudge; no nudge turn and no deeper check), `jira:closeouts` (threadId → the passed Done's closeout draft: `CloseoutDraft` in `lib/jira-done-check.ts`; deleted on submit, Skip Jira and leaving Done), `jira:closeout-ops` (threadId → op ids a closeout submit queued; Undo and the Done dedupe count them as Done ops whatever the comment says; pruned on ack and cancel), `jira:in-flight` (op ids a sync pass claimed and has not acked; kept across restarts, so the next pass re-applies them replay-safely and its ack clears them).
- Closeout: a passed Done (check pass, Confirm done, Mark done anyway) queues nothing. It stores a draft per linked ticket not already done: the `doneSummary` template, with the old ticket-update transition rule as the default (`transitionBlock` names why not). The operator's `jira_closeout_submit` (Post & close) queues each comment and chosen transition through `onceQueued`; `jira_closeout_skip` drops it; `jira_closeout_draft_with_agent` sends one turn through `sendIfIdle` asking the agent to call `focus_board_closeout_draft({ key, body })`, which only replaces a draft body (capped at 4,000) and never submits. That tool is selected whenever Jira is on and refuses unless the calling thread has a draft naming the key. The column's all-done-still-open fix still queues directly.
- Undo: a sync pass claims each op (`store.claim`, under the store lock) right before applying it and skips one that is gone; `store.cancel` (the card's Undo, `jira_undo`) removes only ops that are queued and not claimed, so an op being sent reads as too late. Ops queued with `threadId: null` (column drift fixes) have no card Undo. Undo reverses any Done whose ticket ops it fully cancels (every linked key's Done-summary comment and transition to done still queued), whether the Done came from a passed check, Confirm done or Mark done anyway; if any linked ticket's Done op was already sent, Done stays. Undo is race-free only with the built-in sync: the legacy `jira queue` / `jira ack` CLI reads and acks without claiming. An undone Done does not restore a pin parked when the card went to Done (Mark Not Done does).
- Only-door rule: `threads.send` is called only from `lib/jira-idle.ts` `sendIfIdle` (re-reads status right before the send, mode `"start"`, refuses non-idle threads). Everything else calls `sendIfIdle`. Guarded by `tests/jira-running-threads.test.ts`.
- Exec rule (gate + `tests/security-no-process-execution.test.ts`): no `child_process` in `server.ts`, `app.tsx`, `lib/`, `components/` (comments included) except `lib/jira-exec.ts`, which may only `execFile` the literal tools `acli` and `gh` with an argument array (no `import(` / `require(`, and `child_process` only on its one static import line) (60 s timeout, 64 MiB buffer, absolute path resolved from `PATH` plus `/opt/homebrew/bin`, `/usr/local/bin`, `/usr/bin`). `shell:true` is banned everywhere. With `jiraEnabled=false` nothing resolves or runs a tool.

## Operator rollout checklist

These steps change the live bb install, so they are deliberately not run by the implementation. Do them in order. `<checkout>` is this checkout's absolute path.

1. Checks:
   `NODE_OPTIONS=--experimental-strip-types npm test && npm run typecheck && npm run gates && npm run build`
   `NODE_OPTIONS=--experimental-strip-types` is needed on Node 22.13.1: the test and build scripts first run `scripts/generate-unreleased.mjs`, which imports a `.ts` file. Newer Node versions strip types by default. This predates the Jira work.
2. `bb plugin install <checkout>` then `bb plugin reload focus-board`. Expected: `bb plugin list` shows focus-board running from `<checkout>`, and the board is unchanged (Jira off).
3. Confirm `focus_board_link_issue` and `focus_board_group_set` still appear in a new thread's tools (the first-ever `bb.agents.configure` registration).
4. Sync runs inside the plugin: no automation to create. The setting "Jira: sync automatically" (`jiraSync`) is on by default, and nothing runs while `jiraEnabled` is false, so the first real acli/gh run happens right after step 6. Prerequisites: `acli jira auth status` shows Authenticated, and `gh auth status` reports a logged-in account. `bb focus-board jira sync` runs one full pass by hand and prints the status (exit 1 with the acli/gh error). Once on, a pass runs about 2 seconds after load and then every minute: idle passes only send queued Jira writes, and a full sync runs when the data is 2 minutes old or you press Refresh in the Jira column or Run sync now on the board's Jira banner (either starts a full pass at once, even with "Jira: sync automatically" off). If a "Focus Board Jira sync" bb automation exists from an earlier setup, delete it (`bb automation list`, then `bb automation delete <id>`).
5. `bb focus-board jira reconcile` (dry run; with no snapshot yet it links from titles and branches only, and has no suggestions or drift). Expected: PT-3878 x4 and PT-3879 x7 auto-links, 0 queued ops (suggestions appear once a snapshot exists).
6. Enable: `bb plugin config focus-board set jiraEnabled true`. Enabling runs one reconcile apply with a fresh plan (board links plus an enrollment reset, so no thread is nudged on day 0). It makes no Jira writes. Rollback: `bb plugin config focus-board set jiraEnabled false` (the board goes back to upstream behavior). Then check: running threads get no new turns, the Jira column appears, no pushes on day 0, and a thread spawned by "Start thread" carries the `jira` metadata (the fake host could not verify the namespace). Then `bb focus-board jira sync`. Expected: ok with about 20 tickets in `bb focus-board jira status`. This is the first real acli/gh run: check the flags, and that status names map (In Progress; Done/Closed/Resolved).
7. Known limits:
   - Archived threads are excluded from the all-done drift check: a ticket whose only other linked thread was archived unfinished can still read as all Done.
   - Jira search-index lag can rarely duplicate a create on replay.
   - A verify turn that ends with no verdict fails the check ("no verdict from the agent"). If the plugin restarts while that turn runs, the card stays verifying until Keep working / Mark done anyway.
   - A gh read that fails for some PRs leaves those PRs out of the snapshot (shown as `gh: N of M PRs unreadable` in `jira status` and the column). A Done drop on a thread linking one of them waits in Done ("checking PRs") for a fresh sync and, after 3 minutes without one, asks for Confirm done instead of bouncing to Needs you; the deeper check still reads "PR status unavailable". Closed (unmerged) PRs count as finished and are listed in the Jira comment.
